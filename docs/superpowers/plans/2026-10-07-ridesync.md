# RideSync Implementation Plan

> **For agentic workers:** Use `superpowers:executing-plans` to implement a selected issue at a time. This plan does not authorize automatic execution or delegation.

**Goal:** Motorcycle camera control for Insta360 X5, ONE RS, GO 3S and GoPro HERO12 Black, plus independent A7670E GPS and external-IMU motion logging to microSD.

**Architecture:** Vendor-neutral camera intent/state contracts feed per-peer adapters with deadlines. Pure protocol codecs, GNSS parsing, session clocks and motion estimation are separate from device transports; logging and health supervision remain independent of camera availability.

**Tech stack:** Pinned PlatformIO/Arduino ESP32 build (legacy R2 environment name); the photographed board is T-A7670E V1.4 with A7670E-FASE GNSS. BLE stack and provisional IMU decisions are documented separately from fitted-hardware qualification.

**Spec:** [Architecture](../../architecture.md), [original brief](../../project_brief.md), [GoPro scope](../../gopro_plan.md), and user requirements for GPS/acceleration/lean logging.

## Global constraints

- Extensible camera registry: target at least four configured cameras; measure actual radio capacity.
- Distinguish desired recording, command response and observed recording; no blind toggle retry/replay.
- Bound software waits/retries/queues/memory and isolate SDK calls whose return time is unqualified; one peer failure cannot abort others.
- Local GPS/motion logs continue through camera loss; invalid/stale/missing data stays explicit.
- Preserve raw specific force/angular rate separately from estimated gravity-free acceleration and lean/pitch.
- Per-model wake and telemetry require evidence; external HERO12 telemetry injection is outside initial scope.
- Pin dependencies, audit applicable licenses and anonymize public hardware fixtures.
- Unknown/unverified capabilities are not successful implementations. Each ticket owns its completion criteria.

## Issue review and delivery policy

All original issues #1–#16 were reviewed on 2026-10-07. Overloaded work was split
without closing or deleting the original tickets. #16 remains the sole roadmap
tracker; it is not an implementation ticket. There are 41 work packages below; #34 extracts bounded mixed telemetry admission
and schema from #12, while #35 extracts shared asynchronous central BLE transport
and #36 extracts pure HERO12 setup codecs from #4 (2026-10-08). Maintenance fixes
#32/#33 are tracked separately. #37 extracts camera-event logging; #38–#42
extract configuration handoff, durable session allocation, local telemetry,
handlebar control/status and worker supervision after a runtime ownership audit.
#43/#44 extract concrete targeted bond removal and explicit application reset
maintenance from #18 after inspection found the reset port still abstract.

Source contracts/group policy can begin independently of camera hardware. GNSS,
SD and raw IMU work must not wait for all camera models. Investigations can close
with evidence-backed limits; dependent implementations remain open if blocked.
Optional Insta360 GPS forwarding does not block a core release when disabled.

For code packages, the implementation starts with a failing behavior test or
minimal hardware reproduction, ends with relevant passing checks, and updates
support/evidence docs. Investigations use captures/decisions; hardware packages
use reproducible physical checks. Do not force a firmware rebuild for prose-only
changes. One scoped issue should normally result in one focused PR or small
commit series. New independently reviewable scope requires an explicit decision;
do not create additional tickets automatically.

**Dependencies:** #15, #22, #8, #23, #9, #24, #11, #13, #18, #30, #42

Own the remaining physical reliability checks in one bounded release campaign, reusing matching component evidence.

**Completion policy:** [Finite acceptance](../../acceptance_policy.md). Physical checks are owned once by #22/#30/#31; #3 retains the first-X5 smoke gate.

- [ ] Publish the exact board/card/sensor/camera firmware/configuration and pass/fail/blocked matrix before the run. Use one 30-minute bench session as the initial smoke/reliability baseline, explicitly not a statistical endurance certification; longer soaks require a stated failure hypothesis or intended ride-duration target.
- [ ] During that session, run one camera loss/reconnect and one ESP32 reset while recording, confirming no automatic command replay; record latency, heap/queue/stack/watchdog observations against predeclared configured budgets.
- [ ] Run one real-driver GNSS startup/READY/NoFix observation and one receive-loss/stale/recovery scenario with an actual verified barrier where recovery is claimed. An indoor NoFix result is valid evidence; outdoor position accuracy is a separately labelled measurement.
- [ ] Run one missing/full-media condition, one blocked-storage/control-progress check, and one active power-cut/readback at each attainable startup/write/after-flush boundary. Record exact observed loss/corruption and preserved files; never require a universal SD durability/return-time bound or auto-format/delete data.
- [ ] For installed IMU hardware, record one stationary/known-axis check, one absent/read-failure case and a short concurrent SD/GNSS sample interval/loss trace. Validate estimated outputs only against the finite independent reference plan from #28; otherwise keep estimates Experimental/invalid.
- [ ] After bench and installation checks pass, perform one short controlled ride for enabled claims and compare logs/reference observations. Record excluded/untested optional features explicitly.
- [ ] Run final CI once for the release candidate and publish support per model/feature. Failed cases produce a bounded corrective change and rerun of affected cases, not an automatically expanding test campaign.
