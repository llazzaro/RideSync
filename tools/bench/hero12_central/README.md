# Isolated HERO12 ESP32 bench probe

Experimental diagnostic for the owner's HERO12 Black, declared screen version
2.32 and Mac-observed Hardware Info firmware `H23.01.02.32.00`, model 62,
Open GoPro API 2.0. Mac observations do not qualify this ESP32 path or the
production adapter. This probe uses the existing pure GoPro codecs, pinned
NimBLE-Arduino 2.3.6 and ESP32 toolchain. It does not initialize SD, modem,
IMU, handlebar GPIO or production settings.

## Explicit control

Send one uppercase command per LF/CRLF line. Wait for its terminal report.
`CONNECT` scans for eight seconds, refuses multiple FEA6 identities, connects,
requests legacy Just Works bonding, discovers and checks all eight endpoint
properties, enables and reads back all four response CCCDs, sends pairing finish, verifies exact returned identity/API (including successful
Hardware Info readiness), then queries
Encoding, Busy and Ready. No recording intent is generated by connect/reconnect. This final diagnostic uses
the official classic shutter tutorial path: it does not require or send the
protobuf external-control claim. That claim returned Unknown in the two
preceding ESP32 setup trials and remains unqualified; it is never reinterpreted
as success. The production adapter still requires successful claim admission.

`REC` obtains fresh Encoding/Busy/Ready, requires stopped/available state,
loads video group 1000, sends explicit shutter on once, then queries Encoding.
`STOP` obtains fresh status and sends explicit shutter off once only if Encoding
is true. Same-state requests are refused without a shutter. Confirmation is
separate from ACK and still requires owner camera-screen and media observations.
`QUERY` reads those three status fields. `DISCONNECT` revokes queued commands
and requests disconnect; it does not send Stop. `STATUS` prints redacted runtime
and NVS refusal counters. Pasted command bursts and foreground busy admission
are refused. Keepalive runs every three seconds while qualified. Each connected
session is bounded to ten minutes. There is no shutter retry or automatic replay.

All radio submissions run in a retained owner task; the serial loop keeps
reporting even if the SDK stalls. ATT phases and camera responses have finite
five-second waits. Connection/security have longer finite budgets. A callback
or ambiguous response timeout poisons admission until reset. A disconnect
submission is not a disconnect observation. The probe retains SDK, callbacks,
queues and owner for boot lifetime; it never deinitializes the host. Queue
loss/oversize notifications refuse further work. It does not measure a hard
SDK/RF cleanup deadline or prove statistical reliability.

## Temporary storage and provenance

Each boot generates a random static local identity. Bonding uses the pinned
RAM config store (`MYNEWT_VAL_BLE_STORE_CONFIG_PERSIST=0`); it is lost at reset.
The camera may retain its side of the temporary bond. No prior camera bond is
deleted. Reconnect checks within the same ESP32 boot reuse that RAM bond;
cold boot restoration remains untested by this probe.

The existing X5 probe's linker wrappers refuse NVS initialization/open and
flash/partition erasure. PHY uses its reviewed full calibration in RAM fallback.
`inspect_link.py` reuses its ELF/store/HAL/NVS-caller checks. Capture a verified
full flash backup before uploading, compare the partition table, independently
verify uploaded regions, and compare the original NVS bytes after upload and
physical tests. Keep backups/captures outside Git. No MAC, camera serial, raw
hardware response or security keys are printed.

Protocol references are [official GoPro BLE setup](https://gopro.github.io/OpenGoPro/docs/ble/protocol/ble_setup/),
[official OpenGoPro command examples](https://github.com/gopro/OpenGoPro/tree/main/demos/python/tutorial/tutorial_modules/tutorial_2_send_ble_commands),
and the pinned codec provenance in [the existing fixture audit](../../../test/fixtures/gopro/README.md).
The [ESP32-C6 GoPro remote author's legacy pairing observation](https://github.com/smillier/GoPro_ESP32C6_Remote)
is a candidate for this experiment, not evidence for this installed HERO12.
No source from that repository is copied. No alternative security fallback is
attempted automatically.

## Verification and bench sequence

From the RideSync root:

```sh
clang++ -std=c++17 tools/bench/hero12_central/test_policy.cpp -o /tmp/ridesync-hero12-policy
/tmp/ridesync-hero12-policy
.venv/bin/pio test -e native -f test_hero12_probe -f test_hero12_adapter -f test_gopro_setup_codec
.venv/bin/pio run -d tools/bench/hero12_central
.venv/bin/python tools/bench/hero12_central/inspect_link.py
```

After retained backup and guarded upload, open one continuous serial owner at
115200 using the documented macOS PassiveSerial procedure. Confirm idle startup
and zero erase refusals. Put the camera in its Quik pairing screen, send one
`CONNECT`, and separately confirm the camera UI. After returning to stopped
Video mode with its card installed, request each of three REC/STOP cycles
separately and retain actual screen/playback outcomes. Explicitly disconnect,
connect again, confirm no recording replay, and query state. Tests remain under
#46/#22; no production capability or support flag is promoted by this probe.

October 14 evidence: two camera-observed REC/STOP cycles, a stopped reconnect,
and one owner-confirmed powered-off wake with classic recovery are recorded in
[the dated report](../../../docs/hardware-results/2026-10-14-hero12-pairing.md).
Both Stop ACKs were zero while the five short confirmation polls still showed
Encoding true; the owner separately confirmed actual Stop. The third cycle,
playback and production control-claim path remain pending. Fourteen added
regression cases passed with the complete 714-case native suite. The standalone
runner and CI-native probe target share the same nine policy/parser cases.
